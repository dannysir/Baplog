# 맛집 지도 서비스 — 설계 문서 v2

> 이 문서는 Claude Code 구현의 기준 문서다. "결정됨"으로 표시된 항목은 임의로 변경하지 말 것. "미정"으로 표시된 항목은 구현 전 사용자와 협의할 것.
>
> **v2 개정 요지:** 서비스의 무게중심이 *추천(개인화)* 에서 **기록·사진·소셜**로 이동했다. 정직한 평가 시스템은 여전히 핵심 차별점이나, 이제 "기록을 떠받치는 정직성 레이어"로 위치한다. 카테고리·취향 회피·taste_profile은 전면 제거됐다. 변경 배경은 §0에 정리한다.

## 0. v1에서 v2로 — 변경 결정 요약 [결정됨]

이전 설계는 "나만의 지도를 채울수록 다음 맛집을 더 잘 찾아준다"는 *개인화 추천* 을 핵심으로 삼았다. 검토 결과 개인화의 두 수단(카테고리 기반 콘텐츠 필터링, 협업 필터링)이 모두 v1에서 작동 불가임이 드러났고(전자는 Google 정책·악의 입력 문제, 후자는 네트워크 부재), 동시에 사진·소셜이라는 더 강한 기록 동기가 부상하여 무게중심을 옮긴다.

| # | 변경 | 이유 |
|---|------|------|
| 1 | **핵심을 기록+사진+SNS로 이동** | 개인화 추천은 데이터·유저가 쌓여야 작동. 사진·소셜은 첫날부터 작동하며 "왜 직접 기록하나"라는 동기 문제(콜드 스타트)를 정면으로 해결 |
| 2 | **카테고리·취향 회피·taste_profile 전면 삭제** | (a) 카테고리는 단일 작성자 모델이라 악의/오입력에 취약한 단일 실패점, (b) 신뢰화하려면 다수결 투표 시스템이 필요해져 입력 마찰↑, (c) Google place_id 외 콘텐츠 저장은 사실상 금지라 자체 카테고리도 회색지대, (d) 이 시스템에서 Google 의존을 hot-path로 끌어들이는 유일한 부품이었음 |
| 3 | **추천의 재정의** | v1은 *비개인화 랭킹*(베이지안 점수 정렬 = 발견 UI)만. *개인화* 추천은 v2에서 협업 필터링으로 도입(카테고리 불필요, 사용자×가게 평가 행렬만으로 작동) |
| 4 | **평가 익명 집계** | 집계 점수(PLACE_SCORE)는 공개, 개별 verdict의 주인은 비공개. SNS 과시 압력이 "정직한 비추천"을 부풀리는 것을 막는 핵심 장치 |
| 5 | **사진 기록 추가** | 핵심 기록 단위. 스토리지·리사이즈·모더레이션이 인프라로 따라옴 |
| 6 | **팔로우 기반 SNS 추가** | 승인제 팔로우 + 친구 피드. 공개 범위 "친구만" |
| 7 | **프라이버시 기본기 추가** | 기록 건별 public/private, 팔로우 승인제, 차단/신고. 방문 위치 이력의 민감성 대응 |

## 1. 서비스 콘셉트 [결정됨]

### 한 줄 정의
**"가본 맛집을 사진으로 기록하는 나만의 지도. 팔로우한 친구들과 나누고, 실제 방문 기반의 정직한 점수로 좋은 집을 발견한다."**

### 핵심 가치 (v1 심장)
1. **나만의 지도** — 내가 가본 가게가 핀으로 쌓이는 개인 미식 지도.
2. **사진 기록** — 각 방문에 음식·가게 사진을 남기는 시각적 일지.
3. **팔로우 SNS** — 친구의 지도·기록을 보고, 팔로우하고, 피드로 둘러봄.
4. **정직한 점수(차별점)** — 실제 방문자만, 짜게, 한 번. "4점이면 진짜 4점"인 신뢰 가능한 공개 점수.
5. **점수 기반 발견** — 그 점수로 좋은 집을 찾는 비개인화 랭킹.

### 풀고자 하는 문제
**기록 동기 (신규 핵심):** 기존 미식 기록은 동기가 약하다(추천 보상은 멀고, 기록은 노동). 사진과 소셜 공유가 "내 기록이 예쁘게 남고 남들이 봐준다"는 즉각적 동기를 제공한다.

**평가 정직성 (유지 차별점):** 기존 맛집 검색의 4가지 한계를 정직한 점수로 해결한다.
1. 리뷰에서 광고를 구분하기 어렵다 → 실제 방문(VISIT) 기록이 있어야 평가(RATING) 가능.
2. 기본 별점이 모두 너무 높다(대부분 4.6+) → 모든 가게를 2.5에서 시작, 점수를 쉽게 주지 않는 베이지안.
3. 한 명의 저평가가 평균을 무너뜨린다 → 사전값을 둔 베이지안 평균.
4. 신규 가게는 평점으로 평가하기 어렵다 → 평가 수가 적으면 자동으로 2.5에 묶임.

### 동기 설계 [중요]
v1은 개인화 추천 보상이 없으므로, 기록 동기는 **추천이 아니라 "기록의 정직함과 소유감 + 소셜 공유"** 에서 나온다. "추천을 잘 받으려고 기록한다"가 아니라 "내 미식 지도를 채우고 자랑한다"가 동기다. UI·카피는 이 방향으로 설계한다.

### 단계 로드맵
- **v1:** 지도 + 사진 + 팔로우 SNS + 공개 베이지안 점수 + 점수 기반 발견(비개인화 랭킹).
- **v2:** 개인화 추천을 협업 필터링으로 도입("비슷하게 평가한 사람이 좋아한 가게"). 카테고리 불필요. RATING 데이터가 그대로 입력이 되므로 스키마 변경 거의 없음.

### 데이터 전략 (단계적 전환)
- **초기:** 자체 데이터 부족 → Google Maps API로 가게 검색·표시(콜드 스타트 통과).
- **성장기:** VISIT/RATING/사진이 쌓이며 자체 데이터 축적.
- **전환:** 자체 데이터 품질이 Google을 능가하는 시점에 점진적으로 자체 점수로 무게중심 이동(인위적 전환 시점 없이 데이터 품질 역전에 따라).

## 2. 평점 시스템 — 베이지안 사전값 방식 [결정됨]

### 핵심 원칙
- 평점 범위: 0 ~ 5점.
- **모든 가게는 2.5점에서 시작한다.** (타베로그 영감 — 낮은 기본값으로 변별력 확보)
- 사용자 입력은 **3단계**: 추천 / 보통 / 비추천. (별점보다 단순)
- 평가가 쌓일수록 2.5에서 양방향으로 움직인다.

### 점수 매핑 [결정됨]
| 입력 | 점수 |
|------|------|
| 추천 (up) | 5 |
| 보통 (neutral) | 2.5 |
| 비추천 (down) | 1 |

> 비추천을 0이 아닌 **1점**으로 두는 이유: 0점은 신호가 너무 강해 소수의 비추천에 점수가 과도하게 무너진다. 1점으로 완충(운영하며 튜닝 가능).

### 베이지안 점수 공식 [결정됨]
```
bayesian_score =
  (up_count * 5 + neutral_count * 2.5 + down_count * 1 + PRIOR_WEIGHT * 2.5)
  / (up_count + neutral_count + down_count + PRIOR_WEIGHT)
```
- `PRIOR_WEIGHT`: 사전값 무게. **초기값 10** (상수로 분리해 운영 중 조절 가능하게 구현).
  - 클수록 2.5에 오래 묶여 보수적, 작을수록 소수 평가에도 빠르게 움직임.
- 평가가 전혀 없으면 점수 = 2.5 (신규 가게 자동 처리).

### "보통(neutral)"의 동작 [결정됨 — 의도된 강한 하향력]
"보통"은 numerator에 2.5를 더하므로, **현재 점수가 2.5보다 높은 가게는 끌어내리고 낮은 가게는 끌어올린다.** 즉 무게중심을 2.5로 강하게 당기는 능동적 힘이다. (이전 문서의 "점수를 2.5에서 움직이지 않는다"는 설명은 부정확했으므로 정정함.)

- 예: 추천 50개만 → 4.58. 추천 50 + 보통 50 → `(250 + 125 + 25)/110` ≈ **3.64**. 보통 50개가 4.58을 3.64로 끌어내림.
- **이는 의도된 동작이다.** 압도적으로 좋은 가게가 아니면 4점대가 나오지 않게 하는 변별력 설계의 핵심.
- **UI 함의 [중요]:** "보통"은 사용자 직관(나쁘지 않았다)과 달리 좋은 가게 점수를 깎는다. 입력 라벨을 중립어("무난해요")보다 **"특별히 추천하진 않아요"** 쪽으로 무게를 실어 동작과 인식을 일치시킨다.

### 동작 예시
- 추천 5개: `(25 + 25)/15` ≈ **3.33**
- 추천 50개: ≈ **4.58**
- 추천 100개: ≈ **4.77**

### 점수의 성격 및 인플레이션 대응 [결정됨]
**점수는 절대 품질을 나타낸다.** z-score·백분위 등 상대화 방식은 배제(점수가 다른 가게에 의존하면 절대 품질 약속이 깨짐).

**알려진 한계 — 평점 인플레이션:** 사전값은 "표본이 적을 때"의 과대/과소평가는 해결하나, "표본이 많을 때"의 인플레이션은 해결하지 못한다. 리뷰가 충분히 쌓이면 점수가 실제 추천 비율 평균으로 수렴하는데, 사용자는 대체로 추천을 많이 누르므로 다수 가게가 4점대로 몰린다. 평균 계열 방식의 공통 한계.

> 참고: PRIOR_WEIGHT를 리뷰 수에 따라 키우는 방식은 해결책이 아니다(모든 가게를 동등하게 끌어내려 변별력은 그대로이고, 신뢰도 높은 가게가 가장 억눌리는 역설).

**대응 전략 — 평가자 가중 [결정됨 — 지금은 미구현, v2 이후]:** 추천을 남발하는 평가자의 표는 가볍게, 까다로운 평가자의 표는 무겁게 가중(`up_count`/`down_count`를 가중 합으로, 사전값 구조 유지). 각 가게 안에서 완결되어 절대 품질 성격을 해치지 않는다.

> **주의 — selection bias:** "추천 비율 높음 = 후한 평가자"로 단순 가중하면, 사실은 "갈 데를 잘 고르는 사람"을 페널티 줄 수 있다(자기가 좋아할 곳만 가면 추천 비율이 당연히 높다). 단순 버전은 이 함정을 인지하고, rater bias model로 정교화할 때 보정한다. RATING에 평가자(userId)가 이미 있어 추후 도입 시 스키마 변경 거의 없음.

### 평가 익명 집계 [결정됨 — SNS와의 충돌 방어]
SNS가 붙으면 "친구가 보니까 비추천 누르기 민망"하여 점수가 부풀 위험이 있다. 이를 막기 위해:
- **집계 점수(PLACE_SCORE)는 공개**, **개별 RATING의 주인(누가 어떤 verdict를 줬는지)은 비공개.**
- 피드·프로필에는 "방문했다 / 사진을 남겼다"는 노출하되, **그 가게에 어떤 평가를 줬는지는 노출하지 않는다.**
- 효과: 정직하게 비추천해도 친구에게 들키지 않아 짠 평가가 살아남고, 합산된 공개 점수의 신뢰성이 유지된다.

## 3. 데이터 모델 / 스키마 [결정됨]

### 엔티티 관계
```
USER  ||--o{  VISIT      : records
USER  ||--o{  RATING     : gives
USER  ||--o{  PHOTO      : uploads
USER  ||--o{  FOLLOW     : follows (follower)
USER  ||--o{  FOLLOW     : followed (following)
PLACE ||--o{  VISIT      : has
PLACE ||--o{  RATING     : receives
PLACE ||--o{  PHOTO      : depicts
PLACE ||--||  PLACE_SCORE: aggregates
VISIT ||--o{  PHOTO      : contains   (사진은 방문에 귀속)
```

### USER
| 컬럼 | 타입 | 설명 |
|------|------|------|
| id | uuid (PK) | |
| provider | string | "google" \| "kakao" \| "naver" |
| provider_id | string | 각 제공자 고유 ID |
| nickname | string | |
| created_at | timestamp | |

> **taste_profile 제거 [결정됨]:** 카테고리 삭제로 채울 어휘가 없어졌다. v1에서 제거. v2 협업 필터링은 RATING 행렬로 작동하므로 taste_profile 불필요.
>
> **인증 [결정됨]: 소셜 로그인 전용(구글/카카오/네이버). 자체 비밀번호 없음.** 보안 표면 축소 + 계정 양산 방어. 유니크 `(provider, provider_id)`로 중복 가입 방지. OAuth 처리(토큰 교환·사용자 조회)는 **반드시 백엔드(`apps/api`)**, client secret은 서버에만.
>
> **[미정]** 인증 구현 방식 — 백엔드 직접 OAuth vs Supabase Auth 등. Expo에서 카카오·네이버 모바일 연동은 구글보다 설정이 많음(주의).

### PLACE
| 컬럼 | 타입 | 설명 |
|------|------|------|
| id | uuid (PK) | 내부 식별자 |
| google_place_id | string (unique) | Google place_id. **캐싱 제한 면제 — 유일하게 영구 저장 허용되는 Google 데이터.** |
| created_at | timestamp | |

> **[결정됨] PLACE는 place_id만 저장한다.** 이름·카테고리·평점 등 다른 Google 콘텐츠는 저장하지 않는다. 표시 시 지도 SDK로 직접 표시하거나 백엔드가 실시간 호출(재사용 캐싱 없음). 카테고리 자체를 v2 설계에서 제거했으므로 카테고리 실시간 호출도 없다.

> **유니크 `(user_id, place_id)` [결정됨]:** 한 사용자는 한 가게에 평가 1개만(수정 가능). 반복 평가 조작 차단.
>
> **aspects(다축 평가) 필드 제거 [결정됨]:** "평가는 최대한 단순하게" 방향에 따라 단일 verdict만 유지. 다축은 필요해지면 별도 `RatingAspect` 테이블로 정규화 도입(현재 미도입).
>
> **익명성 [결정됨]:** verdict의 주인은 집계에만 사용하고 피드·타인 화면에 노출하지 않는다(§2 평가 익명 집계).

### PHOTO [신규]
| 컬럼 | 타입 | 설명 |
|------|------|------|
| id | uuid (PK) | |
| user_id | uuid (FK) | 업로더 |
| place_id | uuid (FK) | 어느 가게 |
| visit_id | uuid (FK, nullable) | 어느 방문에 귀속(선택) |
| storage_key | string | 스토리지 객체 키(URL 아님 — 서명 URL은 조회 시 발급) |
| width | int | 원본 폭 |
| height | int | 원본 높이 |
| visibility | enum(public/private) | 건별 공개 범위 |
| status | enum(active/pending/removed) | 모더레이션 상태 |
| created_at | timestamp | |

> **저장 원칙:** DB에는 객체 키·메타데이터만, 바이너리는 오브젝트 스토리지(§5). URL을 직접 저장하지 않고 조회 시 서명 URL 발급(접근 통제).
>
> **모더레이션 [중요]:** 공개 SNS이므로 신고 경로 필수(§5). 음란물·타인 사진·저작권 침해 대응.

| 컬럼 | 타입 | 설명 |
|------|------|------|
| id | uuid (PK) | |
| follower_id | uuid (FK) | 팔로우 거는 쪽 |
| following_id | uuid (FK) | 팔로우 받는 쪽 |

> **유니크 `(follower_id, following_id)`:** 중복 팔로우 방지. `follower_id != following_id` 검증은 앱 레벨.
> **승인제 [결정됨]:** 공개 범위가 "친구만"이므로 아무나 내 동선을 보지 못하게 승인 후 accepted. 차단은 별도 `Block` 테이블 또는 status 확장(미정).

### PLACE_SCORE (집계 캐시)
| 컬럼 | 타입 | 설명 |
|------|------|------|
| place_id | uuid (PK) | |
| up_count | int | 추천 수 |

| down_count | int | 비추천 수 |
| bayesian_score | float | 미리 계산된 점수(기본 2.5) |

> RATING 추가/변경/삭제 시 카운터와 `bayesian_score`를 함께 갱신하는 캐시. 점수 조회는 이 한 줄만 읽음. 동시성·정합성 주의는 §7.

### Google Places API 정책 준수 [중요]
- **place_id 외의 Places 콘텐츠(이름·평점·리뷰 등)는 캐싱/저장 금지.** place_id만 영구 저장 면제(12개월 초과 시 갱신 권고). 현재 정책 기준 비-place_id 콘텐츠의 임시 캐싱 허용은 사실상 좁으므로 보수적으로 "저장 안 함"을 유지.
- 이름·카테고리 등 표시 데이터: (a) 가공 없으면 클라이언트 지도 SDK로 직접 표시(가장 안전), (b) 가공 필요 시 백엔드 실시간 호출, **재사용 캐싱 안 함**.
- Google 평점/리뷰 표시 시 출처 표시(attribution) 의무, 저장/재가공 불가. 초기 큐레이션에 쓸 때는 **실시간 호출 → 그 자리에서 윌슨 점수 등으로 필터링**만 하고 저장 안 함.
- 네이버/카카오 등 다른 상용 지도 API도 저장·DB화 제한(네이버 "리턴 즉시 1회 사용"). 어느 API든 동일 원칙.
- 약관 링크: Terms(`cloud.google.com/maps-platform/terms`), Service Specific Terms(`.../maps-service-terms`), Places 정책(`developers.google.com/maps/documentation/places/web-service/policies`), Place IDs(`.../place-id`).
- 주의: 약관 해석은 법적 판단 영역이므로 규모를 키울 때는 전문가 확인 권장.

## 4. 발견 / 랭킹

> 방향성은 결정됐으나 세부 파라미터는 구현하며 튜닝.

### v1 — 비개인화 랭킹 [결정됨]
"우리 점수로 좋은 집"을 보여주는 발견 기능. 개인화가 아니라 **PLACE_SCORE 정렬**이 곧 추천이다. 카테고리 없이, 유저가 적어도, 첫날부터 작동한다.
- 예: "이 지역 우리 점수 높은 집 순", "친구들이 최근 추천한 집".
- 지역/거리 필터는 좌표 기반(지도 SDK). 가게 메타데이터 저장 없이 동작.

### v2 — 개인화 추천 [결정됨 — 미구현]
협업 필터링("비슷하게 평가한 사용자가 좋아한 가게"). 사용자×가게 RATING 행렬만으로 작동하므로 **카테고리 불필요**. 유저·평가가 충분히 쌓인 뒤 도입. 콘텐츠 기반(카테고리 매칭)은 v2 설계에서도 제외(카테고리 자체를 제거했으므로).

### 신규 가게 발견 (평점 외 신호)
평점이 쌓이기 전 신규 가게는 행동 신호로 노출: 재방문율, 사진/방문 수, 친구 방문 여부.

### 초기 큐레이션 — Google 평점 보정 (사용 시)
초기 자체 데이터 부족 구간에 Google 평점을 거름망으로 쓸 경우, 단순 평균이 아니라 **윌슨 점수 하한**(또는 동일 철학 보정)을 실시간 적용. 리뷰 수가 적을수록 보수적으로 평가("리뷰 적은데 4.6"을 거름). **저장 없이 호출 시점 계산.**
- **역할 한정:** "콜드 스타트용 임시 거름망"일 뿐 자체 베이지안과 층위가 다름. "구글을 못 믿는다면서 왜 구글로 거르나"라는 모순을 피하려 역할 구분 유지.
- **[미정]** 리뷰 수 구간, 윌슨 컷오프 값.

### 이중 평점 표시 [결정됨]
가게에 **두 점수를 함께 표시**: (1) Google 평점(실시간 호출, 저장 안 함, attribution 필요), (2) 자체 베이지안(PLACE_SCORE).
- **차이 자체가 정보:** "구글 4.6 / 우리 3.2" = "구글에선 높지만 우리 사용자 사이에선 보통".
- **콜드 스타트 주의:** 초기엔 대부분 자체 점수가 2.5. 숫자 "2.5"를 그대로 노출하지 말고 평가 수가 일정 미만이면 "아직 평가 부족 / 첫 평가 남기기"로 표시.
- **위계:** 자체 점수가 정체성이므로 주(主), Google은 참고. 데이터 축적에 따라 위계 조정.

## 5. SNS / 사진 / 프라이버시 [신규 핵심]

### 사진 기록
- 사진은 VISIT(또는 가게)에 귀속되는 핵심 기록 단위. 업로드 → 리사이즈/썸네일 → 스토리지 → 조회 시 서명 URL.
- **인프라 [결정됨]:** 오브젝트 스토리지(Supabase Storage 또는 Cloudflare R2). DB엔 키·메타데이터만.
- **처리 파이프라인:** 업로드 시 리사이즈(원본 과대 방지), 썸네일 생성, EXIF 위치정보 제거(프라이버시).
- **[미정]** 한 방문당 사진 수 상한, 최대 해상도/용량.

### 팔로우 SNS
- **승인제 팔로우** + 친구 피드("팔로우한 사람들의 최근 방문·사진").
- 공개 범위 **"친구(accepted 팔로워)만"** [결정됨]. 전체 공개 안 함 — 위치 프라이버시 보호.
- 피드에 노출: 방문·사진·점수 기여 사실. **노출 안 함: 개별 verdict 내용**(§2 익명 집계).

### 모더레이션 [중요]
공개 SNS이므로 v1부터 필요:
- **신고 기능** — 사진·사용자 신고 경로(최소 요건).
- 신고 시 PHOTO.status를 pending/removed로 전환.
- **[미정]** 자동 필터(음란물 분류 등) 도입 여부·시점. 초기엔 신고 기반 수동 + 사후 검토로 시작 가능.

### 프라이버시 [결정됨]
방문 위치 이력은 민감 데이터(거주지·동선 추정 가능). 다음을 v1 범위에 포함:
- **건별 공개/비공개 토글**(VISIT.visibility, PHOTO.visibility) — 기록은 하되 안 보여주고 싶은 경우.
- **팔로우 승인제** — 동선 노출 통제.
- **차단/신고** — 원치 않는 관계 차단.
- EXIF 위치정보 제거(사진).
- **[미정]** 한국 PIPA 대응 상세(수집·이용 동의, 보관기간, 위치정보 별도 동의 여부). 규모 전환 시 전문가 확인.

### Google Maps 사용 구조 [중요]

## 7. 구현 시 주의사항 (Claude Code 작업용)

- **PLACE_SCORE 정합성 [중요]:**
  - RATING 추가/수정/삭제 시 카운터(up/neutral/down)와 `bayesian_score`를 함께 갱신.
  - **수정 경로 delta:** verdict 변경 시 이전 버킷 -1, 새 버킷 +1을 **한 트랜잭션**에서.
  - **동시성:** 같은 가게 동시 RATING은 카운터 lost-update 위험. 트랜잭션 + row lock 또는 SQL atomic increment.
  - **cascade:** 사용자 탈퇴로 RATING이 `onDelete: Cascade` 삭제될 때 카운터가 자동으로 줄지 않으므로 재계산 로직 필수.
  - **드리프트 방지:** RATING에서 카운터를 통째로 재계산하는 self-healing 배치를 두어 증분 누적 오차 보정.
- **점수 계산 상수 위치:** 점수 매핑(5/2.5/1)과 PRIOR_WEIGHT는 DB가 아니라 `packages/core` 상수. DB엔 원재료(카운터)와 결과(`bayesian_score`)만.
- **평가 익명성:** verdict 주인을 피드·타인 화면에 절대 노출 금지(집계만 사용).
- **사진:** DB엔 storage_key·메타만, 바이너리는 스토리지. 조회 시 서명 URL. 업로드 시 리사이즈·썸네일·EXIF 위치 제거.
- **Places API 호출 위치:** 반드시 백엔드. 클라이언트 직접 호출 금지(키 노출 + 정책 위반).
- **OAuth secret 위치:** client secret은 백엔드에만.
- **다운로드/업로드 권한:** 사진 업로드·신고 등 사용자 행위는 명시적 트리거로만.

## 8. 평점 조작 방어 및 한계 [결정됨]

### 현재 방어선
- **같은 계정 반복 평가:** `Rating @@unique([userId, placeId])`로 DB 레벨 완전 차단.
- **다중 계정(sockpuppet) 완화:**
  - VISIT 검증 — RATING은 실제 VISIT 기록이 있어야 작성 가능.
  - 소셜 로그인 전용 — 계정 양산 비용 상승.
  - 베이지안 사전값 — 소수 가짜 추천은 2.5(PRIOR_WEIGHT 10)에 희석(추천 5개로는 ~3.3까지만).

### VISIT 생성 강도 — 마찰 vs 위조의 핵심 트레이드오프 [미정 — 중요]
VISIT은 두 역할을 동시에 진다: (1) **플라이휠 연료**(기록 — 마찰 낮을수록 좋음), (2) **평가 자격 게이트**(위조 막으려면 마찰 높을수록 좋음). 탭 한 번(길찾기)으로 VISIT이 생기면 가짜 계정이 트리비얼하게 평가 자격을 얻어 "광고 구조적 차단"이 무력화된다. 권장 설계:
- **느슨한 VISIT(기록):** 탭/길찾기로 생성. 개인 지도·피드에만 사용, **평가 자격은 주지 않음.**
- **검증된 VISIT:** GPS 근접(이상적으론 목적지 체류시간)으로 생성. **이것만 RATING 자격 부여.**
- 스키마 영향: VISIT에 `verified`(또는 `method`) 필드 1개 추가로 구현 가능.
- 트레이드오프: GPS 검증은 위치 권한 + 위치 결합 VISIT 저장이라 §5 프라이버시와 충돌. 권한 진입장벽도 발생.

### 남은 한계와 향후 대응 (우선순위순)
1. 다중 계정을 완전히 막진 못함 — 장치들이 "비싸고 효과 적게" 만들 뿐.

## 9. 미정 항목 정리 (구현 전 협의 필요)

1. 비추천 점수 1점 유지 여부(운영 튜닝).
2. PRIOR_WEIGHT 운영값(초기 10).
3. **VISIT 생성 강도 — 느슨/검증 2층 분리 방식과 검증 수단(근접 vs 체류)** [§8].
4. 인증 구현 방식(백엔드 직접 OAuth vs Supabase Auth 등).
5. 지도/장소 데이터 소스 최종 확정(구글 vs 네이버 — 표시·SDK 측면. place_id만 저장 원칙은 공통).
6. 백엔드 프레임워크(Hono vs Fastify) 및 배포처(Expo=EAS, 웹/백엔드 별도).
7. 사진: 방문당 수 상한, 최대 해상도/용량, 자동 모더레이션 도입 여부.
8. 차단(Block) 구현 방식(별도 테이블 vs FOLLOW status 확장).
9. 초기 Google 큐레이션 기준(리뷰 수 구간, 윌슨 컷오프).
10. 한국 PIPA 대응 상세(위치정보 동의, 보관기간 등) — 규모 전환 시.
11. v2 협업 필터링 도입 시점·알고리즘.
